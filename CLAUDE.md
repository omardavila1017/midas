## Auth / RBAC / Usuarios + Permisos (rediseño 2026-06-05)

Autenticación real vía backend `/api/auth/*` (o JSON local en dev). Control de acceso **a nivel UI** (NO es frontera de seguridad — ver `AUTH.md`; la autorización vinculante la hace el backend/proxy `/api/*`).

**Modelo nuevo: dos roles + permisos por usuario.** Se eliminaron los roles granulares (`abastos`/`contaduria`/`fiscal`/`cobranza`/`mesa_ayuda`). Ahora `Role = 'admin' | 'user' | 'none'`. El acceso a módulos de un `user` NO sale del rol: lo otorga un admin tab-por-tab con switches en el módulo de **Permisos**.

- **Catálogo de roles (en código, no secreto):** `src/config/roles.ts` — `ROLES` (admin `'*'`, user `[]`, none `[]`), `ASSIGNABLE_ROLE_IDS = ['admin','user']`, `roleCanAccess` (solo admin concede acceso por rol), `coerceRole` (colapsa cualquier rol granular legacy o de backend → `user`; `admin`→admin; desconocido/vacío→none), `LEGACY_ROLE_TABS` (diccionario de migración rol-granular→tabs, **solo** para sembrar permisos por defecto). **Cero correos/identidades aquí.**
- **Catálogo de tabs:** `src/config/appTabs.ts` — `APP_TAB_LABELS` (es-MX por `AppTabId`), `PERMISSION_GROUPS` (switches agrupados por sección para la UI de Permisos), `ADMIN_ONLY_TABS = ['users','permisos']` (NO habilitables por permiso — footgun de escalación), `GRANTABLE_TABS`.
- **Registro + permisos (capa UX, `localStorage`):** `src/modules/users/services/accessControlStore.ts` — store `midas.users.registry.v1` (`email → { role: admin|user, permissions: AppTabId[] }`). Se **siembra una vez** desde la fuente de auth conocida (`listLocalUsers()` del JSON local, o `VITE_USER_ROLES`), mapeando el rol granular previo a permisos por defecto vía `LEGACY_ROLE_TABS` para que nadie pierda acceso al migrar. API: `listManagedUsers`, `upsertUser`, `removeUser`, `setUserRole`, `setPermission`, `setPermissions`, `getGrantedTabs`, `canAccess(email, sessionRole, tab)` (decisión central), `subscribeAccessChanged` (CustomEvent + `storage`). NO es seguridad — editable por el cliente.
- **Mapeo correo→rol legacy (`.env`):** `VITE_USER_ROLES` (CSV `email:rol`) + `VITE_DEFAULT_ROLE` siguen existiendo; el parser (`src/config/userRoles.ts`) ahora **coacciona** roles granulares a `user`. Solo se usa como fuente de siembra cuando el JSON local está deshabilitado.
- **Sesión / Contraseñas:** `Login.tsx` (`AuthGate`) consulta `GET /api/auth/session` y `POST /api/auth/login` (`credentials:'include'`); cookie `HttpOnly`; sin tokens en cliente. `authApi.ts` (`changePassword`/`requestPasswordReset`/`completePasswordReset`/`sendUserPasswordReset`) `normalizeRole` usa `coerceRole`. `localAuth.ts` (`roleForUser`→`coerceRole`, `listLocalUsers()` para siembra).
  - **El login arranca con el correo VACÍO** (ya no se prellena con `getPrefillEmail`/último correo) — aplica a login y a "olvidé mi contraseña". `rememberLastEmail`/`getPrefillEmail` siguen existiendo (la sesión recuerda el correo) pero la UI ya no lo inyecta.
  - **Primer ingreso "tipo register" (modo local).** Un usuario que un admin registró en el módulo de Usuarios pero que aún no tiene contraseña define la suya al entrar: `requiresPasswordSetup(email)` (síncrono, solo modo local) detecta "registrado y sin contraseña" y `AuthGate` lo enruta a `FirstLoginForm` (modo `'setup'`), que llama `completeFirstLogin(email, pwd)` → fija la contraseña + abre sesión. "Conocido" = está en el JSON local **o** en el registro (`accessControlStore`); el rol efectivo lo manda el registro y, si no, el JSON. En modo backend `requiresPasswordSetup` siempre es `false`. **Límite del modo local:** el registro + overlay de contraseñas viven en `localStorage` por navegador (no se propagan entre dispositivos sin backend — ver `AUTH.md`).
  - **Entrada explícita "Crear cuenta" (modo local, estilo Atlas).** Además del enrutado implícito de arriba, el login muestra una entrada **"Crea tu cuenta"** (`RegisterForm`, modo `'register'` de `AuthGate`) cuando `isRegistrationAvailable()` (= modo local). El usuario captura su correo + contraseña; `checkRegistrationEligibility(email)` (síncrono, `authApi.ts`) da un mensaje preciso antes de tocar nada: `not_pre_registered` (un admin no lo ha dado de alta), `already_registered` (ya tiene contraseña → inicia sesión), `backend_managed` (modo backend → lo gestiona el servidor) o `eligible` → reusa `completeFirstLogin` para fijar la contraseña + abrir sesión. Misma fuente de verdad que `requiresPasswordSetup`; NO duplica lógica de credenciales. En modo backend la entrada se oculta (el alta la hace el backend). Tests: `Login.register.test.tsx`.
  - **Admin fija contraseñas.** `adminSetPassword(email, pwd)` (modo local → overlay `setLocalPassword`; backend → `POST /api/auth/users/:email/password`). En Usuarios el botón **"Cambiar contraseña"** (`SetPasswordModal`, sin pedir la contraseña actual) sustituye a "Enviar reset" cuando el modo local está activo; en backend se muestran ambos.
  - **`localAuth.ts` es la autoridad de credenciales** (no solo JSON): `hasLocalPassword`/`verifyLocalPassword`/`setLocalPassword`/`openLocalSession`/`getLocalUserRole` operan por correo (overlay > JSON), así sirven igual para usuarios del JSON y para los registrados por un admin. `login()` (`authApi.ts`, modo local) combina JSON + registro; `localLogin()` se conserva como path JSON-only (lo usan sus tests).
  - **⚠️ Contraseña universal hardcodeada (deliberada, 2026-06-10, commit `c08ddc3`).** `HARDCODED_LOCAL_PASSWORD = 'Senda123'` en `localAuth.ts`: vale para TODA cuenta conocida (aun con contraseña propia ya definida) y `currentHashForEmail` cae a su hash, así que `hasLocalPassword` siempre es true y el flujo de primer ingreso/registro queda efectivamente bypaseado. Decisión de rollout para destrabar a todos los usuarios de golpe; **quitar el short-circuit + fallback antes de cualquier despliegue donde el gate de UI deba significar algo** (detalle en `AUTH.md`).
- **Roles + permisos HARDCODEADOS en el JSON (autoritativo, 2026-06-10).** `authLocalUsers.json` es la fuente hardcodeada de **rol Y permisos por usuario**: cada `user` lleva un `permissions: AppTabId[]` (módulos que ve); los `admin` no lo necesitan (ven todo). Dos garantías nuevas para arreglar el bug "los admins no pueden entrar" y la deriva por navegador:
  - **El rol `admin` del roster es AUTORITATIVO:** `effectiveRole(email, sessionRole)` (`accessControlStore.ts`) devuelve `'admin'` si el correo está hardcodeado como admin en el JSON, **sin importar el estado del registro en localStorage** (`hardcodedRoleFor`). Así un registro stale/corrupto que hubiera degradado a un admin a `user` ya no lo puede dejar fuera. `canAccess` y `AuthContext.role` consumen `effectiveRole`. Para un `user` hardcodeado el rol NO es autoritativo (un admin todavía lo puede promover en el portal — override del registro).
  - **Los permisos se SIEMBRAN del JSON** (`buildSeed` lee `permissions`; fallback a `LEGACY_ROLE_TABS` solo en modo env/backend). Para que cada navegador tome los permisos nuevos se subió la versión del registro **`midas.users.registry.v2` → `v3`** (re-siembra forzada; `storageRegistry.ts`). El portal de Permisos sigue siendo editable (override por navegador), pero el set del JSON es el default en TODOS. **Al cambiar roles/permisos en el JSON, sube la versión de `ACCESS_REGISTRY_KEY`.** Tests: `accessControlStore.test.ts`.
- **Identidad UI:** `src/contexts/AuthContext.tsx` (`useAuth → { email, role, expiresAt, can(tab) }`). `can(tab) = canAccess(email, sessionRole, tab)`; el **rol efectivo** (`effectiveRole`) es: admin hardcodeado del roster → siempre admin; si no, override del registro (admin promovió al usuario); si no, el rol de la sesión. Se reevalúa en vivo vía `subscribeAccessChanged`.
- **Permisos hardcodeados = PISO AUTORITATIVO (auto-reparable, 2026-07-08).** Antes los `permissions` del JSON sólo SEMBRABAN el registro una vez por versión; un registro por-navegador stale/parcial (sembrado antes de un cambio en el JSON, o tocado en el portal) dejaba a un `user` sin un módulo que el JSON sí le concede, y sólo se "arreglaba" subiendo la versión del registro (parche recurrente — bug de Blanca sin acceso a Ingresos pese a estar en el JSON). Ahora `getHardcodedFloorTabs(email)` (`accessControlStore.ts`) expone el set del JSON como **piso**: `getGrantedTabs` devuelve la **unión** de ese piso + los extras del registro. Un `user` SIEMPRE ve sus módulos del JSON en TODOS los navegadores, sin depender de la re-siembra — mismo blindaje que `hardcodedRoleFor` ya daba al rol admin. El portal de Permisos sólo puede AGREGAR extras encima; los tabs del piso salen forzados ON con chip **"Fijo"** y switch deshabilitado (para quitarlos se edita el JSON). Consecuencia práctica: **al cambiar los `permissions` de un `user` en el JSON ya NO es obligatorio subir `ACCESS_REGISTRY_KEY`** (el piso se auto-aplica); subirla sólo fuerza además la re-siembra del set editable. Tests: `accessControlStore.test.ts` ("authoritative floor a stale registry cannot drop").
- **Gating en `AppCore.tsx`:** sin cambios de mecanismo — `visibleSections`/`visibleSubTabsBySection` filtran por `can()`; sección sin tabs visibles se oculta; guard redirige al primer tab permitido. `SectionId 'admin'` → tabs `users` + `permisos`.
- **Carga de APIs por permisos (no-admin, 2026-07-08).** Un `user` NO baja las APIs de módulos que no ve. `allowedDatasets` (memo en `AppCore.tsx`) = unión de `TAB_DATASETS` sobre los tabs con `can()===true`; un admin ve todos los tabs → todos los datasets. `requestDatasets` filtra por ese set (choke point de los loaders JDE/TRESS: cxp/cobranza/compras/pagos/nomina/rol/auxiliar), y los boot effects de **bancos** (prime + backfill, que corren fuera de `requestedDatasets`) se saltan si `banks` no está permitido. Se lee vía `allowedDatasetsRef` para no invalidar la identidad de los callbacks estables. `AppCore` sólo monta tras el `AuthGate`, así que `can()` ya es correcto en el primer render. Ej.: Blanca (netflow/venta/collections/fideicomiso/clients) sólo carga `{banks, cobranza, rol}` — nunca cxp/compras/pagos/nomina/auxiliar.
- **Módulos (`src/modules/users/`):** **Usuarios** (`UsersDashboard`) registra correos y su rol admin/user (alta/baja/cambio de rol) y, en modo local, deja a un admin **fijar la contraseña** de un usuario (`SetPasswordModal` → `adminSetPassword`); en backend el alta real para iniciar sesión la hace el backend. **Permisos** (`PermissionsDashboard`) elige un usuario y prende/apaga su acceso a cada módulo con switches (`PermissionToggle`); un admin ve los switches forzados ON, y los tabs del piso hardcodeado salen forzados ON con chip "Fijo". Ambos tabs son admin-only.

## IVA REAL desde el libro mayor (2026-06-03)

El IVA **acreditable** REAL del módulo de Impuestos se lee **directo del libro mayor JDE** (`/JDEdwards/AuxiliarContable`), no se estima. Antes el acreditable REAL se inferia cruzando líneas banco↔ERP contra CXP por folio y **salía en ~0** cuando el cruce fallaba.

> **El IVA CAUSADO NO sale del ledger (corrección 2026-06-04).** Las cuentas de "IVA trasladado" del mayor mezclan el devengado/no-cobrado (por cobrar, pendiente de cobro) con el cobrado, así que sumarlas inflaba el causado muy por encima del impuesto fiscal (que es **base-cobro**) — se veían netos mensuales de cientos de millones. El causado REAL vuelve a leerse de la **cobranza realmente aplicada** (`accumulateCobranzaPaymentIva`), que es la fuente que venía correcta antes de introducir el ledger. El ledger sólo alimenta el lado **acreditable**.

- **Fetch SEPARADO** con cache propio (`auxiliarcontable-iva`), NUNCA expandir `AUX_RECON_PARAMS.objetos` (1010-1020) — eso rompe la conciliación y revive el timeout de 4 min. `fetchAuxiliarContableIvaRange` (`src/services/jde.ts`) hace **descubrimiento en dos fases**: (A) un mes sobre rangos candidato (`AUX_IVA_PARAMS.discoveryObjetos`, default `1100-1299`/`2100-2299`, override `VITE_AUX_IVA_OBJETOS`) → identifica por nombre los objetos de IVA (`discoverIvaObjetos`/`classifyIvaAccount` en `src/domain/ivaLedger.ts`); (B) rango completo solo de esos objetos.
- **Agregación:** `buildIvaLedgerByPeriod` (`domain/ivaLedger.ts`) suma `importe` por periodo/lado (el importe del ledger ES el impuesto, no la base). Clasifica por `nombreCuenta`: ACREDITABLE→creditable, TRASLADADO/CAUSADO→caused, RETENIDO→aparte.
- **Integración:** `buildTaxDashboardView` recibe `auxiliarIvaRecords`. En modo REAL, si el ledger trae **acreditable** (`hasLedgerCreditable`), `accumulateIvaFromLedger` lo emite (`includeCaused:false`) y los estimadores REAL de acreditable (CXP/OC/Auxiliar direccional) se **omiten** para no doble-contar. El **causado** SIEMPRE viene de `accumulateCobranzaPaymentIva` (base-cobro), nunca del ledger. Sin acreditable en el ledger → fallback a estimación de acreditable (comportamiento previo). IVA pagado al SAT sigue desde estados de cuenta. **FORECAST intacto** (reservas en `scenarioForecastRun.ts` usan `ivaMode:'FORECAST'`, no tocan el ledger — las reservas son obligaciones futuras).
- **Boot:** efecto en `AppCore.tsx` (espejo del de auxiliar, cuelga del dataset `'auxiliar'`, falla suave). Heavy store `auxiliarIvaRecords` (`heavyStoreIDB.ts` + `persistence.ts` MidasStore).
- **Diagnóstico runtime:** `window.__midas__.ivaLedger` = `{ recordCount, accounts (objeto/nombre/kind/signo), byPeriod }`. Supuestos a confirmar contra datos reales: rango de objeto candidato, patrones de nombre en `classifyIvaAccount`, y el signo de `importe` por lado.

## Dos motores: MOTOR 1 (Histórico Reconciliado) + MOTOR 2 (Proyección Corto Plazo) (2026-06-03)

El motor canónico está partido en **dos motores nombrados y testeables**, en archivos físicos separados, orquestados por `buildMovements` (que corre el prorrateo Citi una vez sobre la lista compuesta). Ambos son funciones **exportadas** que reciben `{ monthly, inputs }` (tipo `BuildArgs`). Layout (`src/modules/shared-finance/calculation-engine/`):

- **`canonicalProjection.ts` — API pública / punto único de entrada.** `buildCanonicalProjection` (corre `computeBaseCashFlow` + compone los motores), el orquestador `buildMovements`, `prorateCitiConcentradoraByClient` y `hasSufficientCanonicalData`. **Re-exporta** los dos motores + los tipos públicos (`CanonicalProjectionInputs`/`CanonicalMonthlyPoint`/`CanonicalProjectionResult`) para no generar churn de imports — los consumidores y tests siguen importando desde aquí.
- **`canonicalProjectionShared.ts` — tipos públicos + constantes de clasificación + helpers transversales** (`cleanDate`, `clientDisplayCounterparty`, `resolveInflowSubcategory`, `cxcFacturaKey`, `filterCobranzaByCompany`, `usableJdeProviderCategory`, `INCOME_SUBCAT_*`, `CITI_CLIENT_SUBROLE`). No emite movimientos; no importa de los motores ni del orquestador (sin ciclos).
- **`historicalReconciledEngine.ts` → `buildHistoricalReconciledMovements` — MOTOR 1 (≤ hoy).** La verdad histórica del efectivo: `bank:` (estado de cuenta), `internal-recon:` (neto de traspasos internos, **ancla la caja al saldo bancario real** — no borrar), y rellenos sin-banco `cobranza-historic:` / `auxiliar-historic:`. Owns el filtrado de traspasos internos + cuentas neutras del catálogo.
- **`shortTermProjectionEngine.ts` → `buildShortTermProjectionMovements` — MOTOR 2 (> hoy).** Datos reales de corto plazo, cada uno fechado por **su regla**: Cobranza/CXC abierto + **ROL** (viaje ejecutado aún no facturado → ingreso futuro fechado por la **regla del cliente**: días de crédito + día de pago + frecuencia; ROL se CONSERVA, es la señal temprana) + Viajes Especiales (ingresos); CXP + Órdenes de Compra (`F_Recepcion`+`D_Credito`, regla del proveedor) + Nómina TRESS (egresos). ## Bancos: revalidación de días cacheados vacíos (2026-06-10)

El daily-cache (IDB) guardaba `[]` PARA SIEMPRE para un día pasado de `/bancos` si el API respondió vacío — pero tesorería sube los estados de cuenta a JDE **con atraso**, así que un navegador que consultó el día antes de que el dato llegara quedaba envenenado: nunca volvía a pedir ese día (el delta-watermark `lastSeen` además lo excluía del rango) y ese usuario veía días en blanco que a otros usuarios sí les aparecían. Fix en tres capas:

- **`BANKS_EMPTY_DAY_REVALIDATE_DAYS = 14`** (`src/services/jde.ts`): un día pasado cacheado **vacío** dentro de la ventana se re-pide en vez de servirse del cache; el refetch reescribe la entrada (sana en cuanto JDE tiene el dato). Días vacíos fuera de la ventana (festivos/fines de semana legítimos) siguen saliendo del cache. Aplica en `fetchBankStatements` (single-day, prime) y en `fetchBankStatementsRange` (el reader borra la entrada con `deleteDailyCached` y re-encola el día; opción `revalidateEmptySince` para ampliar la ventana).
- **Delta-sync floor** (`refreshBankStatementsRange`, `AppCore.tsx`): el rango del backfill SIEMPRE incluye la ventana de revalidación (`rangeStart = min(rangeStart, today − ventana)`) — sin esto el watermark saltaba los días envenenados para siempre. Días con datos siguen saliendo del cache (barato).
- **Saneo one-time 60d**: marker `midas.banks.emptyDayHeal.v1` (localStorage, registrado en `storageRegistry.ts`). Ausente → la primera pasada amplía la ventana a 60 días para sanear caches envenenados viejos; se escribe cuando el rango regresa datos. Tests: `jde.test.ts` ("revalidación de días pasados cacheados vacíos").

Costo: ~4-7 requests extra a `/bancos` por boot (los días genuinamente vacíos de las últimas 2 semanas). NO quitar la escritura de `[]` en días vacíos (evita repegar al API dentro de la misma sesión); la ventana es quien repara.

## Frescura de datos: revalidación de Compras / Pagos / Bancos (Etapa 1, 2026-06-17)

Causa raíz de las quejas "datos incorrectos / atorados" (juntas de finanzas 2026-06-17): Midas cachea por día/mes y **no re-pedía** registros ya cacheados, así que algo que cambia de estado en JDE DESPUÉS de cachearse quedaba stale para siempre — OCs en $0 que nunca se actualizan, máquinas con distinto # de registros. El cache layer ganó dos parámetros de revalidación selectiva (espejo de `revalidateEmptySince` de bancos), de modo que sólo se re-pide lo relevante sin re-pedir todo el histórico:

- **`fetchRangeWithMonthlyCache({ revalidateMonths })`** (`dailyApiCache.ts`): un `Set<YYYY-MM>` de meses que se re-piden aunque estén cacheados (sobreescriben el cache). Lo consume `fetchComprasRange(cia, from, to, { revalidateMonths })`.
- **`fetchRangeWithDailyCache({ revalidateSince })`** (`dailyApiCache.ts`): umbral `YYYY-MM-DD`; días pasados `>= revalidateSince` se re-piden. Lo consume `fetchPagoProveedorRange(from, to, { revalidateSince })`.
- **Compras (boot effect, `AppCore.tsx`):** por cía construye `revalidateMonths` = últimos `COMPRAS_REVALIDATE_MONTHS` (3) meses calendario **+** el mes de **cada OC aún en estado no-terminal** (`compraEstado(r) ∈ {sinEntrada, porPagar}` — las únicas que todavía pueden moverse), con piso `COMPRAS_MAX_REVALIDATE_LOOKBACK_DAYS` (540). Si un mes a revalidar es más viejo que el lookback estándar, extiende el `from` de esa cía (los meses intermedios salen del cache, baratos). Las terminales (`facturada`/`cerradaWorkflow`/`cancelada`) NO se re-piden.
- **PagoProveedor (boot effect, `AppCore.tsx`):** además del delta por watermark, baja el `from` a `today − PAGOS_REVALIDATE_DAYS` (21) y pasa `revalidateSince` para re-pedir esa ventana — cubre pagos capturados con atraso sobre un día ya cacheado.
- **Bancos manuales (Bajío/Santander):** la ventana steady-state del backfill subió a `BANKS_BACKFILL_REVALIDATE_DAYS = 45` (las cargas manuales llegan con semanas de atraso; 14d no alcanzaba) y el saneo one-time pasó a marker **`midas.banks.emptyDayHeal.v2`** con ventana 120d (re-sanea caches envenenados abril/mayo). El single-day path sigue en `BANKS_EMPTY_DAY_REVALIDATE_DAYS = 14`.

Tests: `dailyApiCache.revalidation.test.ts`. **No es la corrección del $0 en sí** — ese era un bug del SP `SP_Compras_Auditoria_IA` (lado JDE/BD, ya corregido: usa la cantidad abierta `PR UOPN`); esta capa sólo garantiza que el dato corregido **reemplace** el $0 cacheado.

## Empresas internas y cuentas pagadoras propias en Planeación (2026-06-22)

Tesorería reportó que el bucket **"Proveedores sin categoría"** de Planeación mezclaba cosas que NO son proveedores externos: empresas internas del grupo (MULTICARGA, clasificación JDE **"Filiales"**) y filas etiquetadas con la **cuenta de banco PROPIA** origen ("Sin identificar · BANAMEX 70141027881"). **Reconciliación de traspasos internos → categoría `INTERNAL_RECON` (2026-06-02).** Los traspasos entre cuentas propias se detectan y se descartan del flujo (`classifyMovement(...).kind === 'internal'` + cuentas neutras del catálogo). Con ~$18B de traspasos circulando (2.4× el flujo real), la detección es ~99% simétrica pero el residuo (<1% ≈ $158M) hacía que la **caja Base saliera negativa aunque el banco real estuviera positivo** (+$85.8M): la caja se reconstruía netando solo movimientos reales, asumiendo simetría perfecta de la detección. Fix: `buildMovements` (`canonicalProjection.ts`) acumula el neto descartado por `(cia, mes)` y re-emite **un** movimiento `internal-recon:` con categoría **`INTERNAL_RECON`** = `Σ ABONO − Σ CARGO` internos. Eso ancla la caja al saldo bancario real sin re-inflar los brutos con los miles de millones individuales (emitirlos todos reventaría el conteo de movimientos / OOM). `INTERNAL_RECON` queda **fuera** de los brutos de Ingresos/Egresos pero **cuenta en el saldo**; status `REAL` + fecha pasada → sobrevive el filtro de Base. `buildHistoricalMonths.closingCash` (cashFlowEngine) ya hacía lo equivalente sumando TODOS los movimientos; `computeBaseCashFlow` (dashboardEngine) sigue recomputando `closingCash` desde `income−expense` (sin internos) — esa divergencia del `monthly[]` es preexistente y no afecta la tabla, que usa el run del escenario sobre `movements[]`. **No borres `INTERNAL_RECON` ni el bloque de re-emisión** creyendo que es ruido: ancla la caja a la realidad bancaria. La ventana de pareo cross-day ±3d (`buildPairMatchedKeys` en `netCashFlowEngine.ts`) es de la misma tanda.

**Detección de cuentas propias sembrada desde el catálogo de cuentas (2026-06-10).** `buildOwnAccountsIndex` (`netCashFlowEngine.ts`) ya NO depende solo de los estados de cuenta cargados: se siembra SIEMPRE con el catálogo estático (`bankAccountsCatalog.json`) — dígitos de cuenta (con/sin padding) **y CLABE completa** (solo íntegra, 18 dígitos). Motivo: los traspasos SPEI entre cuentas propias referencian la CLABE destino en el concepto, y los traspasos a cuentas del grupo sin estado de cuenta cargado (reserva, dotación, otra cía) escapaban a la detección y aparecían en Planeación como `AP_PAYMENT` "Sin identificar · BANCO cuenta" bajo "Proveedores sin categoría · proveedores" (la regla `pagadora|proveedores` de `bankAccountFlowCatalog.ts` promueve todo CARGO no identificado de una pagadora a AP). `buildOwnAccountDetector` excluye los identificadores de la PROPIA cuenta por dígitos normalizados y por estructura de CLABE (3 banco + 3 plaza + 11 cuenta + 1 control) — sin esa auto-exclusión, un SPEI real entrante que imprime la CLABE beneficiaria (la propia) se marcaría interno. `INTERNAL_BENEFICIARIES` además cubre TODAS las razones sociales del grupo presentes en el catálogo (fragmentos tolerantes al truncado bancario, ≥12 chars distintivos). El cambio vive en la única fábrica del índice, así que TODOS los consumidores (`MOTOR 1`, conciliación Auxiliar×Bancos, Bancos, predictivo) quedan alineados y el cuadre Planeación==banco se conserva. Tests: `internalTransfers.test.ts`.

**(2026-06-10b) El detector escanea también los campos `InF_ADI_1..3` crudos, con re-unión de dígitos troceados.** Causa raíz de los traspasos que SEGUÍAN cayendo como "Sin identificar · BANAMEX <pagadora CM>": cuando `InF_ADI_1` trae leyenda limpia ("PAGO A TERCEROS"), `parseConcepto` (jde.ts) la adopta como `concepto` y NUNCA expone `InF_ADI_2` — que es donde viene el detalle real del traspaso ("P589  00877732401 a 7013870885 1 SERVICIOS T DE N?21 Pago de …") con la **cuenta destino del grupo troceada por espacios de ancho fijo**. `buildOwnAccountDetector` ahora escanea `concepto`+`referencia`+`infAdi1..3` colapsando whitespace ENTRE dígitos POR CAMPO (`joinDigitRuns` — nunca concatena campos antes, para no fabricar números cruzando fronteras de campo). **Sólo el detector de cuenta-destino mira `InF_ADI`**: los patrones de nombre/RFC/leyenda NO, a propósito — `InF_ADI` imprime también al ORDENANTE ("Pago de <empresa propia>") en pagos reales a terceros, así que escanear nombres ahí marcaría como interno todo pago legítimo (caso pineado en test). La auto-exclusión de la cuenta origen (dígitos + CLABE estructural) sigue cubriendo ABONOs reales que imprimen la CLABE propia. Mismo punto único (`classifyMovement`/`isInternalTransfer` consumen el detector), así que todos los consumidores y el cuadre quedan alineados.

`CellOverride` vs `FinancialAdjustment` precedence (decided — no longer ambiguous): `applyAdjustmentsToMovements` mutates at the **movement** level first; `applyCellOverridesToBuckets` mutates at the **bucket** level afterward, at render. If both touch the same concept/bucket, **the `CellOverride` wins** (REPLACE replaces, DELTA adds on top). Historical buckets (before `asOfDate`) are not overridden.

6. **Trend top-off (opt-in, non-base)**: `buildTrendTopOffMovements` (`src/domain/predictive/trendTopOff.ts`) injects synthetic `forecast:trend:` movements that lift each future month to the Holt-Winters trend without double-counting. Computed AFTER the supplier schedule (its movements are the "committed" baseline) and only when the **Tendencia** toggle is on. Each owns its own persisted flag (`midas.projection.trendTopOff` / `midas.planning.trendTopOff`) but both thread the identical args through the shared pipeline. In Planeación the emitted `forecast:trend:` movements carry `subcategory='Tendencia histórica'`, so `conceptKeyForMovement` lands them in their own rows (`INFLOW:AR_COLLECTION:tendencia-historica`, `OUTFLOW:OPEX:tendencia-historica`) — visible and editable per cell like any projected line. They sit **on top of** ROL/CXC, OCs, payroll and the contractual obligations (convenio, fideicomiso DINA, taxes), never double-counting, because the gap baseline is `supplierSchedule.movements` which already includes them.
7. Manual cell overrides (`applyCellOverridesToBuckets`) at render
8. Recompute KPIs and projections via `calculateBaseProjection`

## Base scenario invariant

The Base scenario (`id === 'base'`) is special and non-negotiable:

- Always present (bootstrap in `scenarioBootstrap.ts` ensures it).
- Not deletable.
- No propuestas attached.
- No manual cell overrides.
- No manual entries spliced in (`includeManualEntries === false` for Base in `buildScenarioRun`).
- No tax movement injection.
- **No future.** The Base run additionally drops any movement whose `effectiveMovementDate` is `> today` (cut in `buildScenarioForecastRun`, scenarioForecastRun.ts). Base shows past/today only; future dates appear ONLY in Approved/proposal scenarios. `cxc:`/`purchase:`/`payroll:` records pass the API filter but their projected collection/payment date can land in the future — this date cut removes those from Base.
- **Real short-term API data only.** Base does NOT read the full canonical projection. `buildScenarioRun` filters `source.movements` through `isRealShortTermApiMovement` (FinancialPlanningDashboard.tsx) so Base keeps only: real JDE cobranza (`cxc:` — invoices for executed trips, the business calls this *rol*), JDE purchase orders/receipts (`purchase:` / `po:` — *órdenes de compra*) and real TRESS payroll (`payroll:` without `:forecast:` — *nómina*). It drops rule-projected collections (`client:`), CXP (`cxp:`), recurring providers (`recurring-*`), budget reserve (`budget-opex-gap:`), the synthetic canonical balancer (`canonical-*`), synthetic payroll fill and the opt-in trend top-off (`forecast:trend:`). The shared canonical engine is NOT modified — the cut lives only in the Base run, so Dashboard/Proyección still get the full projection. Don't move this filter into `canonicalProjection.ts`.
- Read-only in the UI (forecast popover shows lock icon).

If you touch scenario selection, persistence, or the spreadsheet editor, validate this invariant explicitly.

## Dark mode

Dark mode is a class strategy (`html.dark`) wired via `src/index.css`. As of 2026-05-14:

- `tailwind.config.js` has `darkMode: 'class'` and CSS variables mapped under `theme.extend.colors` so `bg-card`, `border-border`, `text-foreground` resolve to tokens.
- `:root` defines the OKLCH light palette; `html.dark` overrides every token with a slate-blue dark canvas (hue 248 across all neutrals so the dark UI looks carved from one slab).
- Tailwind utilities with hardcoded literal colors (`bg-white`, `text-gray-900`, `border-gray-200`, etc.) seeded across ~40 components are intercepted by global `html.dark .bg-white { background: var(--card) }` rules in `index.css`. This lets us avoid rewriting every component with `dark:` variants. To escape this override in a specific spot (rare — e.g. branding over a photo), inline `style={{ background: '#fff' }}`.
- Recharts: avoid inline `stroke="#hex"` on `CartesianGrid`. Use `className="recharts-cartesian-grid"` so the CSS rule in `index.css` (`.recharts-cartesian-grid-{horizontal,vertical} line`) governs both modes.
- Native form controls (`input`, `select`, `textarea`) get dark-mode background / color / border from `index.css` directly. Autofill is overridden via `-webkit-box-shadow: inset` trick.
- `color-scheme: dark` on `html.dark` tells the UA to draw native scrollbars + select popups in dark.
- Focus visible ring uses `var(--accent-blue)`; in dark, it gains a 4px blue glow for keyboard discoverability.

## Performance architecture (2026-05-19 hardening — do not regress)

Crash/perf pass landed 2026-05-19. These are load-bearing; re-check before touching the cited files.

- **Grid virtualization — DISABLED (2026-06-10, por decisión del usuario).** `components/spreadsheet/SpreadsheetGrid.tsx` ahora **renderiza TODO** (todas las filas y todas las columnas) y el grid crece a su alto natural — sin scroll vertical interno; sólo el scroll horizontal nativo sigue activo (necesario para la columna sticky de etiquetas). El scroll virtualizado daba problemas persistentes, así que se forzó `measured = false` para reusar la rama que `computeVirtualWindow`/`VirtualRowList` ya usaban en jsdom/primer paint (renderiza la lista completa). **La infraestructura de medición se conserva pero está INERTE** (`computeVirtualWindow`, `VirtualRowList`, `gridGeometry.ts` + sus tests siguen ahí para no propagar churn). Antes la justificación era OOM ("Aw Snap code 5") con daily zoom × muchos movimientos; si regresa la presión de memoria, la palanca a recuperar es poner `measured = true` (no reescribir el render). Las invariantes de scroll de abajo que NO dependen del windowing (minWidth de fila, scroll-into-view keyboard-only, z-index de footers) siguen vigentes; las que sí (clamp de ventana, `overflow-anchor`) quedan latentes con el render completo.
  - **Scroll robustness (2026-06-05).** Three invariants make horizontal/vertical scroll behave: (1) **every column row carries `minWidth: contentWidth`** (`LABEL_COL_WIDTH + columns.length * colWidth`) so its bg/border/hover spans the full scroll width — without it a `width:auto` row only paints to the viewport edge and the right columns look "sin fondo" when scrolled right; (2) **scroll-into-view is keyboard-only** — `moveSelection` sets `scrollSelectionIntoView.current=true` and the effect early-returns unless the flag is set, so a granularity flip (`colWidth`) or a row-count change (bucket expand / background refetch) never yanks the viewport back to the selection; (3) the container is `overscroll-contain` so reaching an edge doesn't chain-scroll the page; (4) **(2026-06-10)** the container sets `overflow-anchor: none` — without it the browser's scroll anchoring picks a recycled row as anchor and re-pins `scrollTop` against every virtualization commit, which locked vertical scroll entirely when a big bucket (Proveedores sin categoría) was expanded. Also 2026-06-10: the two sticky footers stack (`Neto` at `bottom: ROW_HEIGHT`, Caja at `bottom: 0`) — both at `bottom: 0` overlapped and hid Neto while scrolling. Overscan is `COL_OVERSCAN=5` / `ROW_OVERSCAN=8` (one frame of slack on fast flings); (5) **(2026-06-10b) the virtualization window is clamped to `[0, count]` on BOTH axes** via `computeVirtualWindow` (`gridGeometry.ts`, the single window math for rows and columns). Without the upper clamp on `start`, scrolling past the end of a section (routine when a huge Egresos bucket is expanded — the Ingresos window overshoots) produced `start > count` → the leading spacer (`start × ROW_HEIGHT`) inflated the section beyond its real height **and grew 1px per 1px scrolled**: the grid bottom became unreachable and, on bucket collapse / granularity flip with right-scroll, the viewport went blank with no self-recovery (the oversized spacer kept the browser from re-clamping `scrollTop`/`scrollLeft`). Invariant pinned by `gridGeometry.test.ts`: `leadPx + rendered + trailPx === count × itemSize` for ANY scroll offset; (6) **(2026-06-10c) the sticky footers (Neto/Caja) render at `zIndex: 22`** — above the row sticky label cells (z 15) and the section header buttons (z 18), below the column header (25/30). At their previous z 5, the labels of rows scrolling behind the footers painted ON TOP of Neto/Caja (phantom rows visible "below" the Caja line that looked unreachable at max scroll) and intercepted footer clicks (clicking Caja toggled a random bucket). Stacking pinned by a test in `SpreadsheetGrid.test.tsx`.
  - **Bucket header totals are precomputed (2026-06-09).** `bucketColumnTotals` (a `useMemo` of `bucketId → colKey → Σ`) feeds `renderBucketRow`. Before this, the header summed over ALL child rows × visible columns on EVERY scroll frame, which froze the grid the moment a huge bucket entered the viewport ("Proveedores sin categoría" can hold thousands of one-row-per-person movements). Keep the sum out of the per-frame render path — recompute it only when the run / overrides / columns change.
  - **Pagos a personas → "Personal y nómina" (2026-06-09).** `macroBucketForSupplier` (`providerCategoryGeneralization.ts`) rescues AP_PAYMENT movements that have NO resolvable provider category instead of dumping them as hundreds of one-row-per-person "Proveedores sin categoría" lines. JDE pays finiquitos/honorarios/reembolsos through cuentas por pagar, so two signals re-bucket them to **Personal y nómina**: (1) EXACT — the paying bank account is a nómina account (`subcategory` carries the subRole `proveedores_nomina`/`nomina_operadores`, which generalizes to Personal y nómina); (2) HEURISTIC — `isPersonName(counterpartyName)` (no razón social / digits). Display-only re-bucketing — never touches amount/date/category, so cash totals and the bank-recon invariant are unaffected. `supplierCategoryGroupLabel` (SpreadsheetGrid) drops underscore-bearing subRoles so they don't fragment into `· proveedores_nomina` sub-buckets. NOTE: this is NOT dedup against TRESS — historical nómina = the bank charge (≤ hoy), TRESS payroll is projected forward only (> hoy), so they don't double-count; if TRESS historical nómina is ever wired into the model, it must be deduped against these bank payroll charges.
  - **Category coverage round (2026-06-10).** `generalizeCategoria` now covers the FULL raw-category vocabulary of the bundled catalogs (was 6.9% falling through to "Proveedores sin categoría"): deaccent normalization (`NEUMÁTICOS` failed `/neumat/`), new patterns with data-verified buckets (`PLATAFORMA`→TI, `CONVENIO SENDEX`→Flota, `Pensión`→Personal, govt `IMPUESTOS`/`predial`→**Impuestos**, …), and `macroBucketForSupplier` falls back to the catalog lookup when the movement's `providerCategory` exists but doesn't generalize. Coverage is pinned by a data-driven test (`providerCategoryGeneralization.test.ts` walks every category in `providerCatalog.json` + `proveedores-clasificacion.json` — a new unmapped category fails the test; run `npx vite-node scripts/analyze-provider-categories.ts` after catalog updates). Income side: `resolveInflowSubcategory` rule 5b routes uncrossed ABONOs on `unidadNegocio==='MULTICARGA'` accounts to the (pre-existing but never-emitted) `Multicarga` bucket. `scripts/demo-cuadre.ts` is an executable end-to-end demo of the GL×Banco → canonical → Base → bank-recon cuadre.
  - **Category visuals.** Bucket + section headers are color-coded by `bucketVisuals.ts` (declarative `label → { Icon, color }`, indexed by the base label before ` · subcategoría`). Decorative only — never touches classification/amount/order (that's `planningRowTaxonomy.ts`). Sections are green (Ingresos) / red (Egresos); subtotals + the Caja line inherit the same accent (Caja goes red when negative).
- **Scenario pipeline off the main thread.** `buildScenarioForecastRun` runs in `src/workers/scenarioForecastRun.worker.ts` via `src/modules/shared-finance/hooks/useScenarioRunWorker.ts`. Contract: cache hit = sync (unchanged); miss = post + return the scenario's previous run (stale-while-recompute, never freezes); no `Worker` (jsdom) = sync fallback; `runVersion` bump re-reads the cache. Heavy invariant inputs (`sourceMovements` ~100k + catalogs) are sent ONCE per version and cached in the worker — per-run posts ship only light deltas, so no main-thread structured-clone per edit/flip. `needsHeavy` response = worker lacks the bundle → hook forces a resend. Don't reintroduce posting full args every call. Mirrors the `useFinancialProjectionSource` pattern.
- **Granularity-bounded window.** BOTH `FinancialPlanningDashboard` and `FinancialProjectionDashboard` bound weekly/daily to a near window (monthly = natural year). Proyección originally lacked this → the month→week→day flip blew up to ~365-730 buckets × scenarios and OOM'd ("error 5"). Keep the `deferredGranularity`-keyed window; never widen daily back to the full year.
- **Cache-first instant boot.** The splash (`bootTasks` in `App.tsx`) gates ONLY on `catalog` + `companies` (local/cached, fast). Banks are cache-first (open instantly with hydrated statements) + background revalidate — NOT a splash gate. Boot hard-timeout is **8s** (was 240s). Do NOT re-add `banks` to `bootTasks` or restore the long timeout; that reintroduces the 100-240s splash hang.
- **dailyApiCache.** `ensureMemoryReady` loads via `getAll()` (one callback — the old `openCursor()` fired ~2163 main-thread callbacks/623ms at boot) + a background prune at `CACHE_RETENTION_DAYS` (800 ≈ 2.2yr, must stay ≥ the 2yr Holt-Winters window). Don't revert to the cursor or drop the prune (unbounded `memoryIndex` → GC thrash / OOM over weeks of use).
- **Memory-OOM defense (2026-06-01).** With ALL companies on a normal laptop, the renderer can OOM ("Aw Snap") when switching modules — raw records (compras ~334k, cobranza, nómina 24m, banks) + the ~227k canonical + worker copies + run cache exceed Chrome's per-tab heap ceiling. `src/services/runtimeGuardian.ts` defends in layers: (1) **adaptive heap sampling** — 15s at rest, **2.5s once heap ≥60%** (a fixed 15s interval missed the spike); (2) pressure handlers fire at **75%** (was 85% — too late) to free rebuildable caches, **emergency** at **90%** as a soft last resort; (3) a **persistent post-mortem trail** (`midas.runtime.lastTrail.v1`, registered in `storageRegistry.ts`) written on every sample/nav with a `cleanExit` flag — set false at boot, true on `pagehide`. An OOM-kill skips `pagehide`, so next boot logs "sesión anterior NO cerró limpio" + the active module + heap. Inspect with `window.__midas__.runtime.getLastTrail()`. The **app-level pressure/emergency handler lives in `AppCore.tsx`** (effect near the nav tracker, ~800), NOT only in the finance dashboards — those unmount with the 1-tab keep-alive cap, which previously left **Nómina with zero registered handlers** exactly when it OOM'd. It clears `clearProjectionRunCache` + `clearProjectionSourceCache` + `resetScenarioRunWorker` (terminates the scenario worker → drops its ~100k heavy bundle; lazy-recreated, jobs rejected are all `.catch`-handled); emergency also navigates heavy tabs → `bancos` with a toast. Do NOT move this back into the dashboards only. **Still-open follow-up:** the raw `comprasRecords`/`nominaRecords` arrays held in `AppCore` state for ALL companies are the base heap floor — loading them on-demand per tab (vs. always-in-state) is the durable fix, deferred.

## Risks that bite

1. **Inverting the terminology again.** Simulación / Escenario / Propuesta in UI vs. proposal/scenario/adjustment in code. Check both before renaming.
2. **Breaking the Base scenario.** Any active-scenario change can accidentally allow editing or attach a propuesta to base. Validate.
3. **Assuming new persisted shape.** `localStorage` can hold partial / legacy payloads. Use the normalizer; never read raw fields blindly.
4. **Doc drift.** This file is reality at the time of writing. If you change architecture, update this file in the same PR.
5. **Heavy compute on the main thread.** Forecast and reconciliation are non-trivial. Move new heavy compute into `src/workers/` instead of growing `useEffect` recompute loops.
6. **Duplicate adjustment calls.** `applyAdjustmentsToMovements` is deterministic; calling it twice on the same input is wasted CPU per scenario eval. The fix landed 2026-05-14 — don't reintroduce.
7. **JDE timeout creep.** 120s is the current ceiling. If you raise it, document why; longer hangs make the boot orchestrator feel broken.
8. **Removing the global dark-mode CSS overrides.** ~40 components rely on the `html.dark .bg-white` family of rules in `index.css`. Removing them without migrating each callsite to `bg-card` / token variables will visibly break dark mode.
9. **Re-implementing the global exclusion filter.** As of **2026-06-04 the exclusion catalog is EMPTY** — `EXCLUSION_RULES` in `src/domain/companyExclusion.ts` has empty `ciaNumbers`/`namePatterns`/`unidadesNegocio`, so **nothing is excluded** (Multicarga / empresa 33 and BanBajío now count everywhere: bancos, gastos, proyección, KPIs, histórico). BanBajío was a *separate* switch (`excludeBajio`/`isBajioStatement` in `src/domain/bankStatements.ts`, applied in `AppCore.tsx`'s `accountableBankStatements`); that too now **includes** Bajío — `isBajioStatement` survives only to feed the Fideicomiso DINA module. The **matching mechanism is preserved** so exclusions can be re-enabled by adding values to the arrays. If you re-enable: the single predicate is `matchesExclusionIdentity` (identity-only, **blanket — no date boundary**, drops historical rows too); it lives ONLY in `companyExclusion.ts` and is applied at the JDE normalize layer of every base fetch in `src/services/jde.ts` (`fetchAgedBalances`, `fetchCobranza`, `normalizeCobranzaPayments`, `fetchCompras`, `fetchPagoProveedor`, `fetchNomina`, `fetchBankStatements`, `fetchRol` — via `dropExcludedByCia`; `*Range` variants delegate), the company-selector sites (`filterActiveCompanies` in `App.tsx`), and the `bankStatements` display memo in `AppCore.tsx` (covers persisted IDB / daily-cache / manual uploads that bypass `fetchBankStatements`). Do NOT apply it inside `canonicalProjection.ts` (double-filter bug — the cut is upstream, downstream inherits it). See `EXCLUSION_RULES.md`.
